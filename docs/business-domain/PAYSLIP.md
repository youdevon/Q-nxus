# Payslip Domain Specification

## 1. Purpose

A Payslip is the official employee-facing statement of earnings, deductions and net pay produced from an approved Pay Run.

A Payslip must reflect the immutable payroll result used for payment.

It must not calculate payroll independently and must not read current Employee or Compensation values in a way that changes historical results.

The Payslip belongs to the Payroll domain.

---

## 2. Domain Ownership

Primary owner:

- Payroll Domain

Shared consumers:

- Employee self-service

- Reporting

- File Management

- Notifications

- Audit

- Administration

- Finance support

The Payslip may display selected information from People and Payroll snapshots, but its source of truth is the approved Pay Run result.

---

## 3. Payslip and Pay Run Relationship

Every Payslip must reference:

- One Employee

- One Pay Run

- One Payroll Period

- One approved payroll result

- One Organization

A Payslip must not exist independently of a Pay Run result.

One Employee may receive multiple Payslips for the same Payroll Period where there are:

- Correction Pay Runs

- Adjustment Pay Runs

- Supplementary Pay Runs

- Final-payment Pay Runs

- Off-cycle Pay Runs

Each Payslip must clearly identify its Pay Run type.

## 5. Payslip Statuses

### Draft Preview

A temporary preview generated from an unapproved Pay Run.

Rules:

- Must be clearly marked as unofficial

- Must not be delivered as a final Payslip

- Must not be stored as the authoritative Payslip

- May be regenerated

### Generated

The Payslip has been created from an approved Pay Run result.

Rules:

- Financial values must match the approved result

- Document is not yet necessarily available to the Employee

### Ready for Release

The Payslip has passed validation and is ready for delivery.

### Released

The Payslip is available to the authorized Employee or recipient.

Rules:

- Release date and user must be recorded

- Notification may be generated

### Delivered

The Payslip has been successfully delivered through the configured channel.

Examples:

- Employee portal

- Secure email

- Printed copy

- Approved external delivery service

### Delivery Failed

The Payslip could not be delivered.

Rules:

- Failure reason must be recorded

- Payroll result remains unchanged

- Retry must not generate duplicate authoritative Payslips

### Superseded

A later correction or replacement Payslip has become the current official document.

Rules:

- Original remains historical

- Original must not be deleted

- Relationship to replacement must be recorded

### Archived

The Payslip is retained for long-term history and audit.

## 6. Business Rules

### Source

- A final Payslip must be generated only from an approved and locked Pay Run result.

- A Payslip must not recalculate payroll.

- A Payslip must use immutable payroll snapshots.

- Current Employee changes must not alter a historical Payslip.

- Current bank information must not replace the payment snapshot used at the time.

### Identity

- Payslip number must be unique within the Organization.

- Internal ID must never be reused.

- Every Payslip must reference one Employee and one Pay Run result.

- A Payslip version must be retained where regeneration occurs.

### Accuracy

- Payslip totals must reconcile exactly to the approved payroll result.

- Sum of earning lines must equal displayed gross pay.

- Sum of deduction lines must equal displayed total deductions.

- Net pay must equal gross pay minus applicable deductions, subject to the approved Payroll result.

- Currency must be explicit.

- Rounding must match the approved Pay Run.

### Security

- Payslips contain sensitive personal and financial information.

- Access must be restricted to authorized users.

- Employees should normally see only their own Payslips.

- Payroll users may require broader access according to permission.

- Payslip files must not be exposed through public URLs.

- Download links should be time-limited or access-controlled.

- Sensitive delivery must use secure channels.

---

## 7. Payslip Versioning

Payslip versioning may be required when:

- Formatting is corrected

- Organization branding changes

- A corrected Pay Run creates a replacement result

- A delivery file must be regenerated

- A legal or administrative annotation is added

Rules:

- Financial values cannot be changed without a new approved Payroll result.

- Formatting-only regeneration must preserve the same financial snapshot.

- A corrected financial result must create a new Payslip linked to the correction Pay Run.

- Previous versions must remain available for authorized audit review.

- One version should be identified as the current released version.

- Employer insurance contribution

- Statutory employer contribution

The Payslip must clearly distinguish Employee deductions from Employer contributions.

## 11. Year-to-Date Values

Payslips may display year-to-date values for:

- Gross pay

- Taxable earnings

- Income tax

- National insurance

- Pension

- Selected deductions

- Net pay

Rules:

- Year-to-date values must be calculated from approved Payroll history.

- Reversed or corrected results must be reflected accurately.

- Year-to-date totals must respect the Payroll year and jurisdiction.

- Current Payslip generation must not rewrite prior history.

---

## 12. Leave Balances

Leave balances may be displayed where approved.

Possible balances:

- Vacation leave

- Sick leave

- Casual leave

- Other leave categories

Rules:

- Leave remains owned by the Leave domain.

- Payslip displays a read-only snapshot or approved balance.

- Display must not become the authoritative leave record.

- Leave balances may be omitted where data is not reliable or policy does not allow disclosure.

## 16. Release Process

A typical release process is:

1. Pay Run is approved

2. Pay Run is locked

3. Payslips are generated

4. Payslip totals are validated

5. Sample review is completed where required

6. Payslips are marked Ready for Release

7. Authorized user releases Payslips

8. Delivery begins

9. Delivery status is tracked

10. Employees are notified

Release may be delayed until payment confirmation where policy requires.

---

## 17. Bulk Generation

Payslip generation should support bulk processing.

Requirements:

- Run in a background worker

- Show progress

- Continue without blocking the main application

- Record successful and failed items

- Permit safe retry

- Prevent duplicate authoritative Payslips

- Preserve correlation ID

- Notify authorized users when complete

A failure for one Employee should not necessarily fail the entire batch where safe partial completion is possible.

---

## 18. Failure Isolation

Payslip generation or delivery failure must not:

- Change approved Payroll results

- Unlock the Pay Run

- Take down the Payroll module

- Affect HR

- Affect Leave

- Affect other Q-NXUS domains

- Delete successful Payslips

The system should show a clear failure reference.

Example:

> 3 Payslips could not be generated. Approved Payroll results were not changed. Reference: QNX-PAY-SLP-1042.

---

## 19. Retry Safety

Retrying Payslip generation or delivery must not:

- Create duplicate released Payslips

- Send duplicate emails without warning

- Generate conflicting versions

- Alter approved financial values

- Duplicate audit events unnecessarily

Retry operations should use:

- Stable operation ID

- Payslip ID

- Version

- Correlation ID

- Delivery attempt number

- Idempotency check

---

## 20. Corrections

A corrected Payslip must result from a corrected Payroll result.

Rules:

- Original Payslip remains historical.

- Replacement must reference the original.

- Replacement reason must be recorded.

- Employee should be informed where the original was already released.

- Both documents must remain available to authorized Payroll users.

- The current official Payslip must be clearly identified.

---

## 21. Delete, Revoke and Archive

### Delete

Permanent deletion is allowed only where:

- Payslip is a Draft Preview

- It has never been released

- It is not the official document

- No audit or legal retention applies

- User has elevated permission

Final released Payslips must not be physically deleted through ordinary maintenance.

### Revoke

Use where access to a released Payslip must be withdrawn.

Examples:

- Incorrect recipient

- Security concern

- Document under review

Revocation must:

- Preserve the document

- Block Employee access

- Record reason

- Generate audit event

### Archive

Retains the Payslip for long-term history and legal retention.

Archived Payslips remain available according to permissions.
